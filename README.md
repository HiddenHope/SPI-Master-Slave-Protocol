# SPI Master and Slave in Verilog

A Verilog implementation of the Serial Peripheral Interface (SPI) protocol, featuring an SPI Master, an SPI Slave, and testbenches developed using AMD/Xilinx Vivado.

The project focuses on serial communication, clock polarity and phase, finite state machines (FSMs), shift registers, bit counting, and simulation-based verification.

> **Project status:** The recorded SPI Master tests and SPI Slave MOSI reception tests pass in all four SPI modes. Complete master–slave integration, slave-to-master data transmission, and physical FPGA validation have not yet been verified.

## 1. Project Overview

SPI (Serial Peripheral Interface) is a synchronous serial communication protocol commonly used to exchange data between microcontrollers, sensors, memory devices, and other digital systems.

This project implements the two main components involved in SPI communication:

- **SPI Master:** Initiates communication, generates the serial clock, controls the slave selection signal, transmits data, and receives responses.
- **SPI Slave:** Responds to the master when selected, receives incoming serial data, and provides an interface for transmitting data back to the master.

The design uses parameterized data widths, with 8-bit transfers in the current testbenches.

### Project objectives

- Implement SPI communication logic using Verilog.
- Understand clock polarity (`CPOL`) and clock phase (`CPHA`).
- Support SPI modes 0, 1, 2, and 3.
- Implement serial data handling using shift registers.
- Use counters to track the number of bits transferred.
- Use a finite state machine to control the master transaction.
- Develop testbenches to verify the design in Vivado.
- Observe SPI timing and data transfer behavior through simulation waveforms.

## 2. Understanding the SPI Protocol

SPI is a synchronous, full-duplex communication protocol. It uses a clock signal to coordinate the transfer of data between a master and a slave.

### 2.1 SPI signals

The standard SPI interface uses four signals.

| Signal | Full name | Function |
|---|---|---|
| `SCLK` | Serial Clock | Clock generated by the master to synchronize communication. |
| `CS` | Chip Select | Active-low signal used to select the slave. |
| `MOSI` | Master Out, Slave In | Carries data from the master to the slave. |
| `MISO` | Master In, Slave Out | Carries data from the slave to the master. |

### 2.2 How communication works

A typical SPI transaction follows these steps:

1. The master prepares the data to transmit.
2. The master selects the slave by driving `CS` low.
3. The master generates the serial clock according to the selected SPI mode.
4. The master sends data one bit at a time through MOSI.
5. The slave samples the incoming bits and assembles them into a parallel data word.
6. If the slave has data to return, it can transmit it through MISO while the master receives it.
7. After the transfer, the master deasserts chip select by driving `CS` high.

SPI is full-duplex because MOSI and MISO can carry data simultaneously. However, the exact behavior depends on the implementation of both devices.

### 2.3 Serial-to-parallel conversion

Digital systems often process data in parallel, while SPI transfers it serially.

For example, the byte `10100110` contains eight bits. These bits arrive one at a time over MOSI. A receive shift register stores the bits as they arrive until the complete byte can be presented as parallel data.

A bit counter tracks the number of bits received and helps determine when a complete word has arrived.

### 2.4 Important control signals

- **`start`:** Requests a new transaction from the master.
- **`busy`:** Indicates that the master is performing a transaction.
- **`done`:** Indicates completion of a transfer or reception, depending on the module.
- **`rst_n`:** Active-low reset. When asserted low, the relevant internal state is reset.

## 3. SPI Modes

SPI supports four standard modes, determined by two configuration parameters:

- **Clock Polarity (`CPOL`):** Determines the clock's idle level.
- **Clock Phase (`CPHA`):** Determines which clock edge is used to sample data.

In this implementation, the two-bit `spi_mode` input is interpreted as:

- `spi_mode[1]` = `CPOL`
- `spi_mode[0]` = `CPHA`

### 3.1 Mode configuration

| SPI Mode | CPOL | CPHA | Idle Clock Level | Sampling Edge | Data-Changing Edge |
|---|---:|---:|---|---|---|
| Mode 0 | 0 | 0 | Low | Rising | Falling |
| Mode 1 | 0 | 1 | Low | Falling | Rising |
| Mode 2 | 1 | 0 | High | Falling | Rising |
| Mode 3 | 1 | 1 | High | Rising | Falling |

The **leading edge** is the first clock transition away from its idle level. The **trailing edge** is the second transition, which returns the clock toward its idle level.

- When `CPHA = 0`, data is sampled on the leading edge.
- When `CPHA = 1`, data is sampled on the trailing edge.

The master and slave must use compatible mode settings for reliable communication.

Testing all four modes is important because a design that works in Mode 0 may still have timing or edge-selection errors in the other modes.

## 4. SPI Master

The SPI Master controls the SPI transaction. It initiates transfers, generates SCLK, controls chip select, transmits data through MOSI, and receives data through MISO.

The module is parameterized by `WIDTH`, allowing the data width to be configured. The current testbench uses `WIDTH = 8`.

### 4.1 Master interface

| Signal | Direction | Description |
|---|---|---|
| `clk` | Input | Internal system clock. |
| `rst_n` | Input | Active-low reset. |
| `start` | Input | Requests a new SPI transaction. |
| `tx_data` | Input | Parallel data word to transmit. |
| `spi_mode` | Input | Selects SPI mode 0–3. |
| `clk_div` | Input | Controls the SPI clock division. |
| `miso` | Input | Serial data received from the slave. |
| `mosi` | Output | Serial data sent to the slave. |
| `sclk` | Output | SPI serial clock. |
| `cs` | Output | Active-low slave-select signal. |
| `busy` | Output | Indicates an active transaction. |
| `done` | Output | Indicates transaction completion. |
| `rx_data` | Output | Parallel data received from the slave. |

### 4.2 Master operation

The master follows a finite state machine (FSM) to organize a transaction into distinct stages.

The implemented states are:

| State | Purpose |
|---|---|
| `IDLE` | Waits for a transaction request. |
| `LOAD` | Loads the data and prepares the transfer. |
| `ASSERT_CS` | Selects the slave by asserting chip select. |
| `TRANSFER` | Shifts data and coordinates sampling according to the selected SPI mode. |
| `DEASSERT_CS` | Ends the active SPI transaction by releasing chip select. |
| `COMPLETE` | Signals completion before returning to the idle state. |

The FSM separates transaction control from the bit-level transfer logic, making the sequence easier to understand and debug.

### 4.3 Clock divider

The master receives a `clk_div` input to control the generated SPI clock relative to the internal system clock.

The divider affects the rate at which SPI clock transitions occur. Its exact relationship to the resulting SCLK frequency depends on how the divider is implemented in the RTL.

The recorded master testbench uses:

- Data width: 8 bits
- Clock divider: `clk_div = 4`

## 5. SPI Slave

The SPI Slave communicates with the master when selected. It receives incoming data through MOSI and includes signals and logic intended for transmitting data through MISO.

The slave interface uses the system clock and the external SPI signals. Its MOSI receive path has been simulated independently in all four SPI modes.

### 5.1 Slave interface

| Signal | Direction | Description |
|---|---|---|
| `clk` | Input | Internal system clock. |
| `rst_n` | Input | Active-low reset. |
| `start_tx` | Input | Transmit request or control input for the slave transmit logic. |
| `tx_data` | Input | Parallel data intended for transmission to the master. |
| `spi_mode` | Input | Selects the SPI mode. |
| `sclk` | Input | SPI clock generated by the master. |
| `cs` | Input | Active-low slave-select input. |
| `mosi` | Input | Serial data received from the master. |
| `miso` | Output | Serial data intended to be sent to the master. |
| `rx_data` | Output | Parallel word reconstructed from MOSI. |
| `done` | Output | Indicates completion of reception, according to the RTL implementation. |

### 5.2 Receiving data

The slave receive logic uses a shift register and a bit counter.

The basic process is:

1. Detect the appropriate SPI clock edge for the selected mode.
2. Sample the MOSI input.
3. Shift the sampled bit into the receive register.
4. Increment the bit counter.
5. Repeat until the required number of bits has been received.
6. Make the completed word available through `rx_data`.
7. Indicate completion through `done`, according to the implementation.

For an 8-bit transfer, eight sampled bits are required to assemble a complete byte.

The testbench uses the input byte `8'b10100110`, which is hexadecimal `0xA6`. The received parallel word is checked against this expected value.

### 5.3 Transmitting data

The slave interface also includes `tx_data`, `start_tx`, and `miso` for the transmit path.

For successful slave-to-master communication, the transmit logic must load the parallel data, shift it out on the appropriate SPI edge, and maintain correct timing relative to the master's sampling edge.

Although these signals are present in the interface, the recorded tests cover the slave's MOSI receive path rather than fully verifying MISO transmission.

## 6. Simulation and Testing

The project uses AMD/Xilinx Vivado for behavioral simulation.

### 6.1 Running the master testbench

1. Open the Vivado project.
2. Add `spi_master.v` under **Design Sources**.
3. Add `spi_master_tb.v` under **Simulation Sources**.
4. Set `spi_master_tb` as the simulation top.
5. Select **Run Simulation → Run Behavioral Simulation**.
6. Observe the simulation transcript and waveform viewer.
7. Check the reported transmit data, received data, expected data, and PASS/FAIL result for each mode.

The master testbench uses a simulated slave to provide return data through MISO.

### 6.2 Running the slave testbench

1. Add `spi_slave.v` under **Design Sources**.
2. Add `spi_slave_tb.v` under **Simulation Sources**.
3. Set `spi_slave_tb` as the simulation top.
4. Run behavioral simulation.
5. Check the transcript for the received data and PASS/FAIL result for each mode.

The slave testbench generates the SPI clock and sends a known byte through MOSI. It then compares the received parallel data against the expected byte.

### 6.3 What the testbenches verify

The recorded tests verify:

- Master behavior in SPI modes 0–3 for the tested configuration.
- Slave MOSI reception in SPI modes 0–3.
- Correct reception of the test byte in the slave testbench.
- Matching expected and received values in the recorded master testbench.

Passing these simulations demonstrates that the tested paths work for the configurations used. It does not by itself establish correctness for every data width, clock divider, timing condition, or hardware configuration.

## 9. Understanding the Waveforms

The Vivado waveform viewer is useful for understanding the sequence of events during an SPI transaction.

The following signals are particularly useful when debugging the design.

| Signal | What to look for |
|---|---|
| `clk` | The internal system clock. |
| `rst_n` | Reset assertion and release. |
| `start` | The request that initiates a master transaction. |
| `start_tx` | The slave transmit control input. |
| `tx_data` | The parallel word prepared for transmission. |
| `spi_mode` | The selected CPOL/CPHA configuration. |
| `sclk` | The SPI clock's idle level and transitions. |
| `cs` | Whether the slave is selected during the transaction. |
| `mosi` | The sequence of transmitted bits. |
| `miso` | The sequence of returned bits, when provided by the simulation. |
| `rx_data` | The completed received parallel word. |
| `bit_counter` | Progress through the serial transfer, if exposed in the waveform. |
| `busy` | Whether the master is performing a transaction. |
| `done` | When the module indicates completion. |
| Shift registers | How serial bits are assembled or shifted during the transfer. |

### Key waveform checks

- **Clock polarity:** Verify that SCLK idles low for Modes 0 and 1, and high for Modes 2 and 3.
- **Clock phase:** Verify that data sampling and changing occur on the correct edges for the selected mode.
- **Chip select:** Check that `cs` goes low during the transaction and returns high afterward.
- **Bit ordering:** Check that the bits arrive in the expected order. The current testbenches use MSB-first transmission.
- **Receive data:** Compare the completed `rx_data` word against the expected value.
- **Completion:** Observe `busy` and `done` to understand the transaction's control sequence.

Together, the RTL modules, testbenches, simulation transcripts, and waveforms provide a practical demonstration of SPI communication and its implementation in Verilog.
